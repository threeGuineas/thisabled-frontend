# 친구 추천(`GET /recommendations`) — 프론트엔드 연동 가이드

## 개요

- Base path: `/api/v1` → 전체 경로 `GET /api/v1/recommendations`
- 인증: `Authorization: Bearer <access_token>` 필수
- 요청 파라미터: 없음 (페이지네이션/limit 파라미터 없음 — 한 번에 전체 후보 리스트가 옴)

## 응답 스키마

```json
{
  "items": [
    {
      "user_id": "uuid",
      "nickname": "string",
      "bio": "string | null",
      "profile_image_url": "string | null",
      "tags": ["string", "..."],
      "score": 0.0,
      "reasons": ["string", "..."]
    }
  ],
  "message": "string | null"
}
```

- `items`는 `score` **내림차순 정렬**된 상태로 옵니다. 프론트가 재정렬할 필요 없음.
- `tags`는 태그 코드만 옵니다 — 태그 상세(이름/설명 등)가 필요하면 `GET /users/{id}`로 별도 조회해야 함.

## `reasons` 필드 — 프론트가 알아야 할 것

- **개수가 고정돼 있지 않습니다.** 0개일 수도, 1~2개일 수도 있습니다. UI는 `reasons.length`에 따라 유동적으로 대응해야 합니다 (예: 없으면 사유 영역 자체를 숨기거나 기본 문구 처리).
- 문자열 예시: `"관심사가 비슷해요"`, `"비슷한 연령대예요"`, `"공통 친구가 있어요"`, `"관심 있는 콘텐츠가 비슷해요"` 같은 **일반화된 문장**만 옵니다.
- **절대 장애 유형/모드 관련 표현이 섞여 오지 않습니다.** 백엔드가 응답 직전에 "장애/모드/시각/청각/발달" 같은 단어가 포함된 문장을 강제로 필터링해서 제거하기 때문입니다 (`app/services/match.py`의 `sanitize_reasons()`). → **프론트는 `reasons` 배열을 그대로, 필터링 없이 표시해도 안전**합니다.
- 프론트에서 별도로 사용자의 `ui_mode`(시각/청각/발달/기본)를 가지고 "이 사람 장애 유형이 뭘까"를 유추해서 UI에 표시하거나 매칭 이유로 덧붙이는 로직은 **만들면 안 됩니다.** 이게 이 서비스의 핵심 보호 원칙(MATCH-04)입니다 — 사용자가 선택한 UI 모드는 매칭 신호로만 서버 내부에서 쓰이고, 다른 사람에게 절대 노출되지 않습니다.

## 빈 결과(추천 없음) 처리 — `message` 필드

`items`가 빈 배열이면서 `message`가 채워지는 경우가 두 가지 있습니다. 프론트는 이 두 케이스를 **다른 UX로 구분**하는 게 좋습니다.

| 상황 | `message` 값 | 의미 | 권장 UX |
|---|---|---|---|
| 추천할 후보 자체가 없음 (친구/차단/거절 30일 이내/미성년-성인 제외 등으로 후보 풀이 0명), 또는 매칭 모델이 결과를 안 줬는데도 최종 항목이 0개 | `"추천 정보가 부족합니다"` | **정보 부족으로 인한 정상적인 빈 상태.** 억지로 추정해서 추천을 만들지 않겠다는 정책적 선택 (정보가 부족하다고 해서 장애 유형 등을 임의 추정해 억지로 채우지 않음) | "조건에 맞는 추천이 아직 없어요" 같은 **일반 빈 상태 화면**. 에러가 아님 |
| 매칭 모델 서버가 응답하지 않음/타임아웃 (10초) | `"지금은 추천을 만들 수 없어요. 잠시 후 다시 시도해 주세요"` | **일시적 서버 장애.** 사용자 데이터 문제가 아님 | "새로고침" / "다시 시도" 버튼이 있는 **일시적 오류 화면** (재시도 유도) |

- 두 경우 모두 HTTP 상태코드는 **200**입니다 (에러가 아니라 정상 응답 안에 빈 결과 + 안내 메시지로 옵니다). 프론트는 `response.ok` 체크가 아니라 **`items.length === 0 && message` 여부로 빈 상태를 판단**해야 합니다.
- `message`는 두 경우 다르지만 텍스트로만 구분되므로, 정확한 매칭을 위해 **문자열을 하드코딩해서 분기하기보다, 이 문서의 두 메시지를 상수로 관리**하는 걸 권장합니다 (백엔드 메시지 문구가 바뀌면 프론트도 갱신 필요).
- `items`가 있는데 `message`가 같이 오는 경우는 없습니다 (`message`는 항상 `items`가 빈 배열일 때만 채워짐).

## 요약 체크리스트 (프론트 구현 시)

- [ ] `reasons` 배열 길이 가변 대응 (0개 포함)
- [ ] `reasons` 내용은 필터링 없이 그대로 표시 가능
- [ ] UI 모드 기반으로 장애 유형을 유추/표시하는 로직 만들지 않기
- [ ] 빈 결과를 "정보 부족"과 "일시적 장애" 두 가지로 구분해서 다른 문구/버튼 노출
- [ ] `items`는 이미 점수순 정렬되어 있으므로 재정렬 불필요
- [ ] `tags`는 코드값이라 사람이 읽을 이름이 필요하면 별도 API 호출 필요

## 관련 파일 목록 (백엔드)

- `app/api/v1/recommendations.py` — `GET /recommendations` 컨트롤러, `NOT_ENOUGH`/`TEMPORARY` 메시지 상수
- `app/services/match.py` — 후보 풀 필터링(`candidate_pool`), 모델 서버 호출(`MatchClient.score`), 사유 필터링(`sanitize_reasons`)
- `mocks/match_model.py` — 로컬 개발용 매칭 모델 mock 서버 (실제 배포된 MATCH v2 모델의 계약 참고용)
- `docs/ThisAbled_기능명세서_v2_2.md` — MATCH-02-8(미입력 처리), MATCH-03(추천 모델), MATCH-04(추천 보호 원칙) 스펙
